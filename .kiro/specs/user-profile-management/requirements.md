# 用户信息管理需求说明

## 背景与问题

KKMall 当前用户信息能力较薄，`users` 表仅保存手机号、昵称和角色；收货地址虽然已有列表和新增能力，但缺少编辑、删除、默认地址管理和独立用户中心入口；图片上传能力也主要服务于商品后台，无法形成用户头像管理闭环。

主流电商平台通常把个人资料、头像、收货地址和账户入口作为用户中心基础能力。京东帮助中心将收货地址管理放在账户设置中，并覆盖添加、修改、删除和默认地址场景；拼多多隐私政策也将昵称、头像、收货地址、联系方式列为典型用户资料与配送信息。本期目标是先补齐这些稳定共性能力，提升用户下单前后的基础账户体验。

参考来源：

- 京东帮助中心：`https://help.jd.com/`
- 拼多多隐私政策：`https://www.pinduoduo.com/pdd_privacy_policy.shtml`

## 目标与成功标准

- 用户可以在前台查看并编辑个人基础资料。
- 用户可以上传、预览和保存头像图片。
- 用户可以完整管理自己的收货地址簿。
- 结算页优先选中默认地址，减少重复填写。
- 后端 API 继续使用 `/api/v1` 前缀、统一 `ApiResponse` 响应和当前 Spring Security 登录态。
- 前端复用 Vue 3、Pinia、Vue Router、Ant Design Vue 技术栈。

## 目标用户与使用场景

- 登录用户：维护昵称、头像、性别、生日等基础资料。
- 登录用户：在下单前维护收货地址，设定默认地址。
- 登录用户：在结算页快速选择默认收货地址完成下单。
- 平台运营：通过完整用户资料提升用户识别、订单履约和后续会员能力扩展基础。

## 用户故事或用例

### UPM-01 查看个人资料

作为登录用户，我希望进入“我的账户”后看到手机号、昵称、头像、性别、生日和注册时间，以确认当前账户资料。

验收标准：

- 未登录访问时跳转登录页。
- 已登录用户只能查看自己的资料。
- 手机号只展示，不在本期编辑。

### UPM-02 编辑个人资料

作为登录用户，我希望修改昵称、性别和生日，以维护更完整的账户信息。

验收标准：

- 昵称必填，长度 2-32 个字符。
- 性别支持 `UNKNOWN`、`MALE`、`FEMALE`。
- 生日可为空；填写时不能晚于当前日期。
- 保存成功后页面和本地用户信息同步更新。

### UPM-03 上传和保存头像

作为登录用户，我希望上传头像图片，并在账户入口和个人资料页看到新头像。

验收标准：

- 支持 JPG、PNG、WEBP、GIF 等 `image/*` 图片。
- 文件大小上限为 2MB。
- 上传成功返回可访问 URL，并保存到当前用户 `avatarUrl`。
- 上传失败时显示明确错误，不覆盖已有头像。

### UPM-04 地址簿管理

作为登录用户，我希望新增、编辑、删除和设置默认收货地址，以便下单时快速选择。

验收标准：

- 地址字段包括收货人、手机号、省市区、详细地址、默认标记。
- 每个用户最多保存 20 个地址。
- 第一个地址自动成为默认地址。
- 同一用户任何时刻最多只有一个默认地址。
- 删除默认地址后，如还有其他地址，系统自动选择最近更新的一条作为默认地址。
- 用户不能访问、修改或删除其他用户的地址。

### UPM-05 结算页默认地址

作为登录用户，我希望进入结算页时自动选中默认地址，避免每次重新选择。

验收标准：

- 有默认地址时自动选中默认地址。
- 没有默认地址但有地址时，选中列表第一条。
- 没有地址时展示新增地址表单并阻止无地址提交订单。

## 功能需求

1. 新增用户资料查询 API。
2. 新增用户资料更新 API。
3. 新增用户头像上传 API。
4. 扩展用户数据模型，增加 `avatar_url`、`gender`、`birthday` 字段。
5. 扩展地址簿 API，支持详情、编辑、删除、设为默认。
6. 增加地址数量限制、默认地址唯一性和归属校验。
7. 新增前台“我的账户”页面，包含资料卡片、资料表单和地址管理区域。
8. 更新全站顶部登录用户入口，展示头像和昵称，提供“我的账户”“我的订单”“退出登录”菜单。
9. 更新结算页默认地址选择逻辑。

## 非功能需求

- 头像上传需限制文件类型和大小，避免过大文件占用存储。
- API 错误码保持业务可识别，例如 `PROFILE_NICKNAME_INVALID`、`ADDRESS_LIMIT_EXCEEDED`、`UPLOAD_FILE_TOO_LARGE`。
- 数据库迁移必须兼容已有用户和地址数据。
- 地址和资料接口均必须依赖当前登录用户，不能接受前端传入 `userId`。
- 页面在桌面和移动宽度下都可操作，表单项不应重叠或溢出。

## 范围外事项

- 不做会员等级、积分、优惠券和成长值。
- 不做第三方账号绑定、解绑和账户安全设备记录。
- 不做手机号修改、密码登录、实名信息和发票资质。
- 不做省市区标准码库和三级联动数据源，本期继续使用文本输入。
- 不做头像裁剪、审核和历史头像管理。

## 风险、约束与假设

- 当前已有商品详情相关未提交改动，本需求实现需避免回滚或覆盖无关文件。
- 当前上传服务对象路径固定为 `products/`，头像上传需要扩展存储路径而不破坏后台商品上传。
- 现有前端部分中文显示存在编码异常，本需求新增中文文案使用 UTF-8；不主动改动无关页面文案。
- 地址当前位于 `order` 模块，本期可继续复用 `OrderApplicationService` 内现有地址能力，但如代码膨胀明显，应拆出地址应用服务。
- 假设手机号登录和 JWT 登录态继续沿用现有机制。

## 验收标准

- 登录用户可通过顶部菜单进入“我的账户”。
- 用户资料页可展示和保存昵称、性别、生日、头像。
- 用户头像上传成功后刷新页面仍能展示。
- 地址簿支持新增、编辑、删除、设为默认，且默认地址唯一。
- 用户最多保存 20 个地址，超过限制时返回业务错误。
- 结算页优先选中默认地址。
- 后端相关测试通过，前端 `npm run build` 通过。
